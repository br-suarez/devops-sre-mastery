Kubectl de diagnóstico (los que ya corriste)

  • kubectl describe pod <pod> → Last State, Reason, Exit Code, Events
  • kubectl get pod -o jsonpath='{.status.containerStatuses[0].lastState.terminated.exitCode}' → muerte previa en Deployment
  • kubectl get events -n <ns> --sort-by=.lastTimestamp → mejor que describe para events repetidos
  • kubectl exec deploy/<x> -- curl -s -o /dev/null -w "%{http_code}" localhost/path → ver lo que el kubelet ve
  • kubectl top pods → usage real vs límite (OOMKill: límite bajo + usage alto)

Lecciones finas que casi nadie dice

  • QoS: Guaranteed exige requests == limits en memoria Y CPU. Solo memoria = Burstable. Nada de nada = BestEffort.
  • Job template inmutable → field is immutable; remediación: delete + re-apply. Deployments SÍ son mutables (rolling update, nuevo ReplicaSet hash).
  • Reinicio rítmico (intervalos regulares) = probe. Muerte silenciosa sin event = OOM.
  • Probes: liveness = mata y reinicia · readiness = te saca del Service (pod sigue vivo) · startup = bloquea las otras hasta arrancar (apps de arranque lento).
  • App lenta con pods Ready: CPU throttling (limits bajos), DNS lento (ndots:5, CoreDNS), readiness permisiva, dependencias externas.
  • Escalado responsable: "pedí permiso, no perdón" — ownership sin bypassar al dueño de la relación.
  • Current-context primero: kubectl config current-context antes de diagnosticar CUALQUIER cosa — operar contra el cluster equivocado es el error #1 (vivido en el Esc. 3 con kubelabs-final).
  • Node NotReady: scope primero (¿un nodo o todos?) → desde el nodo curl -k https://<api>:6443/healthz separa red de kubelet → systemctl status kubelet + journalctl -u kubelet. Certificados vencidos del kubelet = clásico en edge.
  • Eventos con reintentos: agrupa por patrón, el primer error no siempre es la causa raíz (Esc. 4: primer pull falló por DNS blip, la causa era la imagen).
  • DNS: options ndots:5 = 3 consultas desperdiciadas por nombre externo. Fixes: dnsConfig ndots:1, FQDN con punto final (api.x.com.), NodeLocal DNSCache.
  • Pending + FailedScheduling: no es un crash — es el scheduler: requests > allocatable, affinity, taints sin toleration.

⌨️ kubectl de repaso — lo básico de todo screening

Ver / listar (el 80% de lo que te van a preguntar)

  • kubectl get pods · kubectl get pods -n <ns> · kubectl get pods -A (todos los namespaces)
  • kubectl get pods -o wide — agrega IP y nodo (¿DÓNDE corre?)
  • kubectl get all -n <ns> — pods + services + deployments + replicasets de golpe
  • kubectl get nodes · kubectl get svc · kubectl get deploy · kubectl get jobs · kubectl get ns
  • kubectl get events -n <ns> --sort-by=.lastTimestamp — el historial de qué pasó, ordenado

Describir / ver (cuando algo está raro)

  • kubectl describe pod <pod> — estado, reason del último reinicio, events. EL comando de diagnóstico
  • kubectl logs <pod> · kubectl logs -f <pod> (seguir en vivo) · kubectl logs --previous (logs del contenedor ANTES del último reinicio — clásico de entrevista)
  • kubectl top pods · kubectl top nodes — consumo actual vs límites (necesita metrics-server)
  • kubectl exec -it <pod> -- bash — entrar al contenedor; kubectl exec <pod> -- curl localhost:8080/health — ver lo que la probe ve

Aplicar / editar (con cuidado)

  • kubectl apply -f file.yaml — crear o actualizar
  • kubectl edit deploy <name> — edición en vivo (Deployments SÍ, Jobs NO: template inmutable)
  • kubectl delete pod <pod> — el pod se recrea solo si lo maneja un Deployment (restart del servicio "a lo bruto")
  • kubectl scale deploy <name> --replicas=3
  • kubectl set image deploy/<name> container=<img>:v2 — rolling update manual
  • kubectl rollout status deploy/<name> · kubectl rollout undo deploy/<name> — ver y revertir un update

Contexto / cluster

  • kubectl config get-contexts · kubectl config use-context <ctx> — con qué cluster estoy hablando
  • kubectl cluster-info · kubectl api-resources (qué tipos existen) · kubectl explain pod.spec (documentación integrada)

Truco anti-herrumbre: kubectl <comando> --help y kubectl explain <recurso> responden el 90% de las dudas EN la terminal — también en la entrevista si es hands-on.

🧪 Quizzes — respuestas correctas

Escenario 1 — OOMKill 4/5

  • 143 = SIGTERM graceful (128+15) ✅
  • Penúltima muerte en Deployment → lastState.terminated.exitCode ✅
  • requests==limits solo en memoria, CPU sin definir → Burstable (dije Guaranteed ❌ — Guaranteed exige AMBOS recursos)
  • Probe HTTP 500 → reproducir el endpoint con exec+curl antes de tocar recursos ✅
  • Job immutable → delete + re-apply ✅

Escenario 2 — Probes 5/5

  • Exit 0 + Completed → app sana, algo externo la mata ✅
  • Readiness fallando → pod Running pero fuera del Service, sin reinicio ✅
  • App de arranque lento → startupProbe con failureThreshold amplio ✅
  • Kubelet mata → SIGTERM + grace period; SIGKILL solo si no muere ✅
  • "Borra la liveness" → explicar riesgo + alternativa (arreglar el endpoint) ✅

Escenario 3 — Node NotReady 5/5

  • NotReady a los 40s del último heartbeat (node-monitor-grace-period) ✅
  • Kubelet muerto → pods "frozen" (siguen corriendo, sin reinicios ni probes) ✅
  • Tras 300s de toleration → Terminating → re-scheduling (~5 min en cluster multi-nodo) ✅
  • 5 de 6 nodos NotReady → problema del control plane, no de los nodos (scope primero) ✅
  • Kubelet vivo + conectividad OK → journalctl -u kubelet (certs vencidos en edge) ✅

Escenario 4 — ImagePullBackOff 5/5

  • logs falla — nunca existió contenedor ✅
  • Staging OK / prod muere → registry privado sin imagePullSecrets (en el namespace del POD) ✅
  • 429 → rate limit del registry ✅
  • Eventos mixtos → agrupar por patrón, no quedarse con el primer error ✅
  • Backoff de pull con cap ~5 min ✅

Escenario 5 — DNS 5/5

  • Lentitud intermitente sin resource issues → sospechar DNS primero ✅
  • Pod que solo habla con afuera → dnsConfig ndots:1 ✅
  • CoreDNS muerto → pods corriendo OK, nuevos levantan Running pero funcionales-vegetales ✅
  • FQDN con punto final → evita la search list ✅
  • Pending + FailedScheduling → scheduler (requests/affinity/taints), no un crash ✅
